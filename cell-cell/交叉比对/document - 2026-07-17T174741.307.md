## 总体判断

P1-B3 可以判定为**阶段性通过**：

* 计划提交前检查地址、边、注册表版本与节点状态；
* `apply()` 不重算物理量；
* 同一计划禁止二次提交；
* 中途异常能够恢复 `charge/_q_in/_q_out`；
* 9 项提交测试、B2/B3 合计 20 项测试和 21/21 全量回归均通过。 

因此不应再继续拆单边机制。下一步应进入：

[
\boxed{\text{P1-C：完整世界—皮肤—传输联合资格验证}}
]

但在正式连接所有机制之前，需要把三项提交契约纳入 P1-C 的入口设计。它们不必重新命名为 P1-B3.1，也不代表 B 阶段失败。

# 一、P1-B3 仍有三个需要由 P1-C 接住的边界

## 1. 状态过期检测只比较了 `charge`

当前计划保存的参与节点快照是：

```text
participating_node_snapshots: Dict[str, float]
```

提交前只比较节点的 `charge`；但回滚却已经正确意识到，电容状态还包括：

[
(\text{charge},,_q_{\mathrm{in}},,_q_{\mathrm{out}}).
]



可能出现：

1. 计划生成；
2. 外部过程向节点注入 (+\delta)；
3. 随后又泄漏或转出 (-\delta)；
4. `charge` 回到原值；
5. 但 `_q_in/_q_out` 已改变。

此时：

[
q_i^{current}=q_i^{snapshot}
]

仍会通过，但账本状态已经不是计划生成时的状态。

因此 P1-C 的联合计划应保存完整快照：

[
S_i=
(q_i,\ q_{in,i},\ q_{out,i}).
]

或者生成一个不可变状态指纹：

[
h_i^{state}
===========

H(q_i,q_{in,i},q_{out,i}).
]

这不是要求把所有诊断字段都变成物理状态，而是保证“计划新鲜性”的定义与回滚边界一致。

---

## 2. `AppliedPlanRegistry` 的生命周期需要绑定到物理图

当前防止重复提交依赖外部传入的：

```text
AppliedPlanRegistry
```



若调用方在第二次提交时创建一个新的空 `AppliedPlanRegistry`，理论上同一个计划可能绕过二次提交检查。

所以必须冻结一条生命周期契约：

[
\boxed{
\texttt{AppliedPlanRegistry}
\text{ 必须由物理图或联合调度器长期持有，}
\text{不能由单步调用者临时创建。}
}
]

更稳妥的结构是：

```text
JointThermalRuntime
    .applied_plan_registry
```

或：

```text
ThermalFieldGraphRuntime
    .commit_ledger
```

不必修改 `ThermalFieldGraph` 母本，也可以让新的联合调度对象持有。

还应增加一个测试：

> 使用同一图，但传入一个新建的空提交登记表，再次提交同一计划，仍然必须拒绝。

若当前架构无法做到这一点，就说明提交唯一性仍由调用纪律保证，而不是由结构保证。

---

## 3. 计划还没有显式绑定到具体运行实例

当前计划记录：

* `registry_revision`；
* 地址和边版本；
* 节点 charge 快照。

这可以拒绝缺少节点或状态不同的另一张图。现有测试也覆盖了这两种表现。

但如果复制一张：

* 地址相同；
* revision 相同；
* charge 相同；
* 边版本相同；

的镜像图，计划可能无法判断它是不是原来的运行实例。

如果项目契约是：

> 计划只允许提交到生成它的物理运行实例，

那么需要增加：

```text
runtime_uid
```

或：

```text
registry_instance_uid
```

计划生成时记录，提交时检查。

如果项目有意允许计划提交到完全同构且状态相同的副本，则必须明确写出这种可移植语义。目前测试名称“应用到另一图拒绝”更接近前一种契约，所以建议正式绑定运行实例。

# 二、P1-C 的第一步不是增加测试，而是建立联合一步更新

现在已有三个局部更新路径：

[
\text{世界扩散与泄漏},
]

[
\text{世界—皮肤接触},
]

[
\text{有序过剩热能转移}.
]

还有动态热源：

[
\text{source.release()}.
]

P1-B 的计划只覆盖有序传输，不能保证它与扩散、接触和热源基于同一个时刻的状态。

因此 P1-C 最重要的交付不是“多跑一些组合测试”，而是建立一个范围受限的：

```text
JointThermalStepPlan
```

或：

```text
CoupledThermalStepPlan
```

这不是全项目通用事务框架，只负责当前热物理子系统。

## 联合一步的正确语义

[
X^n
===

(
q_{\mathrm{world}}^n,
q_{\mathrm{skin}}^n,
E_{\mathrm{source}}^n
).
]

从统一快照计算：

[
\mathcal F^n
============

{
J_{\mathrm{diff}}^n,
J_{\mathrm{contact}}^n,
J_{\mathrm{oet}}^n,
P_{\mathrm{source}}^n,
J_{\mathrm{loss}}^n
}.
]

然后：

[
X^n
\longrightarrow
\mathcal F^n
\longrightarrow
\Delta X^n
\longrightarrow
X^{n+1}.
]

即：

[
\boxed{
\text{snapshot}
\rightarrow
\text{compute all flows}
\rightarrow
\text{joint validation}
\rightarrow
\text{aggregate}
\rightarrow
\text{single commit}.
}
]

不能变成：

```text
graph.step()
→ transport.apply()
→ skin.step()
→ source.release()
```

因为那样后面的机制会读取前面已经修改的状态，物理结果再次依赖调用顺序。

# 三、P1-C 建议只拆成三个内部 Gate

# P1-C0：联合计划与统一提交

只完成调度契约。

## `prepare_joint_thermal_step()`

从同一快照计算：

* 热源拟释放功率，但暂不扣除 source；
* 世界扩散通量；
* 世界—皮肤接触通量；
* 环境泄漏；
* 有序过剩热能转移；
* 世界节点净变化；
* 皮肤节点净变化；
* source 拟扣除量；
* 联合稳定性；
* 三级账本预览。

联合稳定性：

[
\eta_i^{joint}
==============

\Delta t
\left[
\frac{
\sum_j\kappa_{ij}
+
\sum_sH_{is}
+
G_i^{env}
}{C_i}
+
\sum_{e:\operatorname{tail}(e)=i}a_e
\right]
\leq1.
]

其中：

[
G_i^{env}
=========

\frac1{R_i^{env}}.
]

V3 已经给出了这个正确的联合公式。

## `apply_joint_thermal_step()`

只能：

* 检查完整状态快照；
* 检查运行实例身份；
* 检查计划未提交；
* 应用冻结后的节点净变化；
* 扣除 source；
* 返回联合回执；
* 中途异常时恢复世界、皮肤、source 与账本。

P1-B 的 `ThermalTransportPlan` 不应删除，它可以成为联合计划中的一个子计划。

# P1-C2：算子与长程资格

## 线性正域

所有有序 tail 全程满足：

[
q_i>0.
]

构造真实运行算子：

[
E^{n+1}=M_EE^n+b.
]

验证：

[
M_{E,ij}\geq0,
]

封闭时：

[
\mathbf1^\top M_E=\mathbf1^\top.
]

同时必须验证真实代码：

[
E_{\mathrm{runtime}}^{n+1}
\approx
M_EE_{\mathrm{runtime}}^n+b.
]

不能只证明一个独立构造的矩阵守恒。

## 过剩边界

在：

[
q_i\rightarrow0
]

附近验证：

* 不出现负传输；
* tail/head 不隐式翻转；
* (q_i\leq0) 后出边功率为零；
* 账本仍闭合；
* 没有数值抖动造成频繁正负穿越。

## 时间步收敛

使用：

[
\Delta t,\quad
\frac{\Delta t}{2},\quad
\frac{\Delta t}{4}
]

运行到同一物理时刻，误差必须下降。

## 冻结段浸泡

热源关闭、拓扑固定、参数固定，运行：

[
5\sim10\tau_{\mathrm{slow}}.
]

验证：

* 能量漂移；
* 非负性；
* NaN/inf；
* 三级账本；
* source 耗尽后的虚假注入；
* 正确稳态。

## 驱动段浸泡

热源开启或 (a_e(t)) 变化：

* 不使用单一 (\lambda_2)；
* 验证有界性与逐步账本；
* 驱动停止后必须能进入冻结段并收敛。

V3 对正域/边界以及冻结段/驱动段的区分已经正确，应直接实施。

# 四、“资格与升级登记表”是正确的，但已经暴露出一处文档漂移

新增的分类法、四个审查点和八字段登记表很好地回应了“降级是否导致方案变形”的担忧。它明确区分了：

* 纠错性撤回；
* 能力暂缓；
* 工程范围限制；

并把真实平流的升级前置写成质量、比热、流率、焓和驱动功账本。

但 V3 前部 P1-A 的历史定义仍写着：

```text
medium-transport
J_i→j^tr = a_ij E_i
```



而后面的当前实现已经改成：

```text
ordered-excess-thermal-transfer
J_e^oet = a_e u_tail^+
```

这正是“方案实施变形”最现实的来源之一：不是代码真的变形，而是总纲中同时存在两套当前定义。

建议立即修正文档：

* 将 P1-A 的机制集合改成当前常量；
* 将旧公式明确标注为历史废弃形式，或直接删除；
* 当前章节不得再出现未钳位的 (aE) 作为生产定义。

同时增加一个很小的文档一致性检查，搜索当前有效章节中是否残留：

```text
AdvectiveThermalLink
medium-transport
J_i→j^tr=a_ij·E_i
方向反转
绝对热能
```

允许它们出现在“已否决假设”和历史说明中，但不能出现在当前接口定义中。
