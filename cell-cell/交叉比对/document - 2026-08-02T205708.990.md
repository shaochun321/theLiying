## 一、模块位置

放在：

```text
nexus_v1/relations/selection_contract.py
```

是目前最合适的。

原因不是“选择机制属于R1”，而是当前候选的输入对象与本体模板来自R1：

[
\mathcal C_i\cong R1
]

S0-a定义的是：

> 多个同等级R1同构候选进入竞争之前，必须满足什么接口和反硬编码约束。

它暂时不值得建立新的顶层目录，例如：

```text
nexus_v1/selection/
```

因为现在还没有真正的：

* 竞争电路；
* 资源动力学；
* 维持与淘汰过程；
* 候选生成系统。

过早创建独立子系统，容易再次让抽象接口脱离实际物理结构。

但要避免让这个模块依赖具体的：

```text
RPrecCircuitT1
RPrecCircuitT2
```

它应该依赖R1的最小公共资格，而不是某条具体时间关系。

真实动力学是否存在更新顺序偏置，要等S0-b候选池运行后再次验证。

因此两项标准需要分成两个层级。

### S0-a：契约级审计

验证接口和验证器不读取语义字段，不产生默认胜者。

### S0-b/S0-c：运行级审计

这不是重复测试，而是：

[
\text{静态契约无偏}
\neq
\text{运行时动力学无偏}.
]

# 三、S0-a应该定义什么

建议只定义六类最小对象，不增加动力学。

## 1. 候选身份

候选身份应当是不透明地址：

```python
CandidateId
```

它只能用于：

* 审计；
* 查找；
* 谱系登记；
* 结果对应。

禁止用于：

* 优先级计算；
* 胜者判断；
* 资源分配；
* 权重初始化差异。

特别不要定义：

```python
candidate_0_is_default
preferred_candidate
expected_winner
```

---

## 2. 候选物理描述

例如：

```python
CandidatePhysicalSpec
```

只包含允许影响动力学的物理参数，如：

* 输入结构地址；
* 输出结构地址；
* trace时间尺度；
* 权重和阈值；
* 局部耗散参数；
* 支撑窗口。

这里需要明确：

[
\text{物理参数差异允许影响结果}.
]

否则所有候选完全同构同参，就不存在可被环境区分的基础。

---

## 3. 存在状态

例如：

```python
CandidateOccurrenceState
```

表示候选是否由物理链路真实发生：

[
o_i(t).
]

它由R1活动或投影谱系产生，不由竞争机制修改。

竞争失败后也不能将其改写为：

```text
未发生
```

---

## 4. 保留状态

例如：

```python
CandidateRetentionState
```

保存：

* 当前维持量；
* 可塑权重；
* 资源配额；
* 衰减状态；
* 后验支撑累计量。

必须保持类型隔离：

```text
CandidateOccurrenceState
≠
CandidateRetentionState
```

不要只靠两个布尔变量区分。

---

## 5. 资源约束

例如：

```python
LocalResourceConstraint
```

S0-a只声明约束：

[
\sum_i p_i(t)\le P_{\max}^{\mathrm{local}},
]

包括：

* 预算量纲；
* 预算所属窗口；
* 候选资源占用读取方式；
* 超预算时必须由后续竞争层处理。

本轮不要实现具体分配算法。

---

## 6. 资格标准

例如：

```python
SelectionQualificationContract
```

记录五项未来通过标准：

1. 无预指定胜者；
2. 标签置换不变；
3. 资源总量受限；
4. 环境改变能够改变占优候选；
5. 占优候选切断后资源能够重新分配。

其中S0-a只能真正审计前两项的**契约部分**。

后三项应标记：

```text
DECLARED_NOT_YET_EXECUTABLE
```

不能因为写进dataclass就标为PASS。

---

# 四、允许读取量与禁止读取量

建议不要只写在注释里，而是形成可验证的数据结构。

## 允许读取

竞争动力未来可以读取：

* 候选真实活动轨迹；
* 局部输入电流；
* trace和collector状态；
* 实际功率或资源占用；
* 后续窗口预测残差；
* 物理发生谱系；
* 可塑性状态；
* 局部时间和作用窗口。

## 禁止读取

动力选择函数禁止读取：

* `relation_type`字符串；
* `candidate_id`的顺序；
* 数组索引；
* 站点的语义名称；
* 测试场景名称；
* `expected_winner`；
* 人工正确答案；
* 报告标签；
* 仅供审计的投影文本。

这里需要注意：

[
\text{站点物理地址}
]

在谱系核验中可以读取，但不能作为：

```python
if site_id == 28:
    priority += 1
```

这样的优先条件。

# 五、本轮自动化测试怎样写才不越界

建议新增：

```text
nexus_v1/tests/test_selection_contract.py
```

只写四类审计。

## T-S0A-1：存在与保留类型不可混用

确认竞争侧不能通过保留状态伪造或删除物理发生。

例如：

* `CandidateOccurrenceState`是冻结对象；
* retention更新不改变occurrence identity；
* 两者不能相互隐式转换。

---

## T-S0A-2：禁止字段拒绝进入选择输入

构造带有：

```text
relation_type
expected_winner
scenario_name
```

等字段的假对象。

验证契约提取器：

* 拒绝；
* 或明确剥离这些字段；
* 最终只输出白名单物理量。

更推荐白名单提取，不要靠黑名单穷举。

即：

```python
SelectionInput.from_physical_state(...)
```

而不是直接把完整R1对象传入未来选择器。

---

## T-S0A-3：标签置换契约不变

创建三个物理参数相同、只有：

* `CandidateId`；
* 名称；
* 列表顺序

不同的假候选。

进行任意置换 (\pi) 后，契约提取出的物理输入多重集合应保持一致：

[
\mathcal P(C_1,C_2,C_3)
=======================

\mathcal P(C_{\pi(1)},C_{\pi(2)},C_{\pi(3)}).
]

注意这里测试的是输入规范化结果，不是候选胜负。

---

## T-S0A-4：相同候选不得产生默认优先级

契约层面对三个完全相同候选调用资格检查时，只能得到：

```text
TIE
UNRESOLVED
NO_PREFERENCE
```

不能返回：

```text
candidate_0
```

但是不要在S0-a实现一个假的“选择函数”来通过测试。

正确测试对象应该是：

```python
contract.assert_no_static_preference(candidates)
```

它只检查：

* 是否有候选专属优先级字段；
* 是否有不同初始化资源；
* 是否有按索引赋权；
* 是否有默认胜者。

它不负责实际选择。

```text
- 候选标签与排列不改变规范化物理输入

- 环境驱动胜者转换
- 竞争后重新分配
```
