但下面这条方向不成立：

[
Occurrence
\rightarrow
binary\ boundary\ pulse
\rightarrow
\Theta.
]

## 唯一阻塞

`Occurrence` 是软件闭合记录：

[
O_\alpha=
(t_{\mathrm{up}},t_{\mathrm{down}},address,epoch).
]

其中 (t_{\mathrm{down}}) 只有发生结束后才知道。因此从完整 `Occurrence` 生成：

[
p_\alpha(t)
===========

\mathbf 1[t_{\mathrm{up}}\le t\le t_{\mathrm{down}}]
]

是**后验重建**，不是实时存在的物理过程。

而且：

```python
physical_carrier = "collector.spiking"
```

只是一个字符串声明，不能让数据类本身获得物理载体资格。

如果Θ读取这个对象，主线会再次变成：

[
\text{软件事件记录}
\rightarrow
\text{关系判断},
]

也就是刚刚试图去除的静态化和符号化。

## 正确的因果方向

现有collector真正可作为候选的是它实时产生的脉冲过程：

[
\boxed{
p_\alpha(t)
===========

# collector_\alpha.activation(t)

\mathbf 1[\text{collector在 }t\text{ 时刻发火}]
}
]

然后分成两条下游：

[
p_\alpha(t)
\longrightarrow
\Theta,\Sigma,\Lambda
]

以及：

[
p_\alpha(t)
\longrightarrow
OccurrenceClosure
\longrightarrow
Occurrence_\alpha.
]

因此必须冻结：

[
\boxed{
Occurrence_\alpha=\mathcal A[p_\alpha],
\qquad
p_\alpha\neq\mathcal B[Occurrence_\alpha].
}
]

`Occurrence`是对物理边界过程的审计和谱系记录，不是物理边界过程的来源。

## R0执行计划应这样修改

### 删除

不要给 `CollectorOccurrenceTap` 增加：

```python
.last_boundary_process
```

也不要从已闭合的 `Occurrence`反向生成供Θ使用的binary窗口。

### 改为

新增一个轻量、实时的：

```text
CollectorBoundaryPort
```

它不创造新信号，只暴露现有collector在每一步的真实输出：

```python
generator_address
carrier_ref          # 指向真实collector，不是字符串
t_step
spike_output         # collector.activation
epoch_id
exists_without_learning
```

这个接口只是对物理过程的有类型访问，不负责：

* 判断发生是否完成；
* 保存 (t_{\mathrm{down}})；
* 生成关系；
* 归一化幅值；
* 从审计记录反推过程。

## 新的关键测试

最重要的测试不再是“能否从Occurrence构造boundary”，而是：

[
\boxed{
\text{即使关闭 OccurrenceClosure 和 finalizer，
boundary port仍然输出真实collector脉冲。}
}
]

具体资格：

1. `spike_output`逐步等于真实 `collector.activation`；
2. 禁用Tap、Closure、Finalizer后，边界过程仍存在；
3. `Occurrence`可以由该过程生成，反方向不成立；
4. G28、G31、G21共用同一个port类型；
5. 地址重命名不改变脉冲轨迹；
6. STDP=0、DA=0时仍成立。

## 修正后的下一步

[
\boxed{\text{R0-2：暴露collector实时发生边界端口，而不是包装Occurrence。}}

之后统一时间算子才可以读取：

[
\Theta_\tau
\bigl(
H_\tau[p_i],
p_j
\bigr),

其中 (H_\tau) 是统一历史保持结构，(p_i,p_j) 是实时物理边界脉冲。
