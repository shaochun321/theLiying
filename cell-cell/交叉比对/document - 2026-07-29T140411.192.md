现在要解决的问题是：

# 本轮应真正新增什么

建议新增一个生产模块，例如：

```text
nexus_v1/events/event_support.py
```

只实现三个核心类型。

## 1. `EventKernelSpec`

描述一种候选事件需要哪些支撑，不执行神经动力学：

```python
@dataclass(frozen=True)
class EventKernelSpec:
    address: GeneratedAddress
    generation_depth: int
    required_port_types: tuple[str, ...]
    required_support_roles: tuple[str, ...]
    output_types: tuple[str, ...]
```

当前只定义一种核：

```text
A_PRECEDES_B_FAST
```

它要求：

* A 的 D1 occurrence / NaturalUnit；
* B 的 D1 occurrence / NaturalUnit；
* `a_prec_b_fast` relation collector；
* relation bundle；
* 局部作用出口；
* 对应物理支撑地址。

---

## 2. `EventSupportBinding`

把某一次实际发生绑定到核上：

```python
@dataclass(frozen=True)
class EventSupportBinding:
    kernel_address: GeneratedAddress

    occurrence_a_address: GeneratedAddress
    occurrence_b_address: GeneratedAddress

    relation_address: GeneratedAddress
    collector_address: StructuralAddress
    bundle_address: StructuralAddress
    physical_support_addresses: tuple[StructuralAddress, ...]

    relation_kind: str
    relation_window: tuple[int, int]
```

它回答：

> 当前这条 (A\prec B) 关系，是由哪一次 A 和哪一次 B 构成的？

这一步最重要的是**实例身份**，不是站点身份。

不能只记录：

```text
site28 → site31
```

必须记录：

```text
occurrence_28_epoch_17 → occurrence_31_epoch_22
```

否则相同站点后来再次发生时，会被错误地拼进旧事件。

---

## 3. `EventInstanceCandidate`

绑定成功后产生一个候选实例：

```python
@dataclass(frozen=True)
class EventInstanceCandidate:
    address: GeneratedAddress
    kernel_address: GeneratedAddress
    support_binding: EventSupportBinding

    t_enter: int
    local_effect_measure: float

    lineage_valid: bool
    support_complete: bool
    qualification_status: str
```

第一版只允许：

```text
CANDIDATE
REJECTED_INCOMPLETE_SUPPORT
REJECTED_LINEAGE_MISMATCH
```

不要马上增加完整的：

* `ACTIVE`
* `EXIT`
* `REARM`
* 残差；
* CPC；
* Xin；
* 事件重写。

这些属于后续 P2-B1K1。

# 外部熵账本本轮怎么处理

本轮**不让账本主动控制事件**。

只保留一个可选的审计字段：

```python
ledger_summary: Optional[PhysicalLedgerSummary]
```

或：

```python
resource_viable: Optional[bool]
```

但第一版不能把它作为事件成立的唯一条件。

因为目前真正经过验证的支撑是：

* 两次 D1 发生；
* trace / collector；
* relation bundle；
* 局部电流作用。

账本目前只负责确认这些结构的物理来源和资源读出，不负责从上层命令事件发生。

所以第一版资格可以是：

[
Q_{\rm K0}
==========

Q_{\rm lineage}
\land
Q_{\rm support}
\land
Q_{\rm local\ effect}.
]

不加入抽象的：

[
Q_{\rm entropy}.
]

等以后实际存在某个 PowerRail、代谢供给或物理门控元件，才通过显式转换算子把资源状态加入事件可维持条件。

# 本轮只做三个测试

## T-EKB-1：完整支撑

给定：

* A 的真实 D1 occurrence；
* B 的真实 D1 occurrence；
* 正确的 (A\prec B) 关系；
* 正确 collector；
* 正确 bundle；
* 已确认局部作用；

应该产生：

```text
EventInstanceCandidate(status=CANDIDATE)
```

---

## T-EKB-2：缺失必要支撑

分别移除：

* A 或 B 的 occurrence 地址；
* relation collector；
* bundle；
* 局部作用证明。

都不得取得候选资格：

```text
REJECTED_INCOMPLETE_SUPPORT
```

这证明“事件”不是因为程序看见一个标签就自动生成。

---

## T-EKB-3：谱系错配

使用：

* 第一次 A；
* 另一轮、不属于该关系窗口的 B；

即使站点仍然是 28 和 31，也必须拒绝：

```text
REJECTED_LINEAGE_MISMATCH
```

这一步最关键。它证明事件绑定的是**具体发生谱系**，不是抽象站点名称。

---

# 本轮不要做什么

不要在 P2-B1K0 中：

* 新增神经元；
* 修改 DA；
* 修改 CPC；
* 修改 STDP 参数；
* 扩展另外三个关系方向；
* 构造完整事件状态机；
* 引入事件概率；
* 引入 Xin；
* 声称形成了 D3 正式事件。

本轮资格只有：

[

]
