我看到了：**P2-B1K0 已经实际落地为生产代码**，而且它完成的功能本身是有价值的——把一条 D2 关系绑定到正确的两次 D1 occurrence，并拒绝缺失支撑和跨 epoch 错配。

但这也确认了我们刚才担心的偏移：

[
\boxed{\text{代码做的是“关系谱系绑定”，名称和阶段却被升格成了“事件元支撑绑定”。}}
]

因此现在不建议回滚代码，但必须立即修正其理论定位。

# 一、实际完成了什么？

当前模块实现了：

[
\rho_{A\prec B}^{(2)}
\longrightarrow
\left(
u_{A,i}^{(1)},
u_{B,j}^{(1)}
\right)
\longrightarrow
\text{物理支撑}.
]

它验证：

* 关系属于哪两次具体 occurrence；
* 需要 collector、bundle 和局部作用证明；
* 相同站点的错误 epoch 不能被拼接；
* D2 地址不再只直接回指皮肤站点。

这正是此前应补的：

[
\boxed{\text{P2-B1X：D1→D2 实例谱系闭合。}}
]

从这个角度看，代码没有白做，也没有损坏底层架构。

# 二、它没有完成什么？

虽然类名叫：

* `EventKernelSpec`
* `EventSupportBinding`
* `EventInstanceCandidate`

但测试没有证明：

* 支撑在真实运行中何时同时出现；
* 支撑如何连续维持；
* 事件何时进入、退出和重新可用；
* 这些支撑共同形成了独立于单条关系的组织；
* 候选结构具有新的未来作用；
* 一个事件与另一个事件的客观边界。

所以当前的 `CANDIDATE` 实际含义只是：

[
\boxed{\text{关系谱系材料完整且一致。}}
]

还不是：

[
\boxed{\text{事件候选已经由过程生成。}}
]

报告本身也明确没有构造 `READY/ACTIVE/EXIT/REARM`，没有引入残差，也不声称形成 D3 正式事件。

# 三、唯一阻塞问题

[
\boxed{\text{不要继续实施 P2-B1K1。}}
]

如果现在继续做“事件核连续状态机”，就会把单条 (A\prec B) 关系预先包装成一个事件类型：

[
A\prec B
\Rightarrow
\text{某个事件}.
]

这会绕过原路线中关键的：

[
D_2\text{关系}
\rightarrow
P2\text{-C关系—关系组织}
\rightarrow
D_3\text{事件／组织资格}.
]

最终可能变成由开发者在 `EventKernelSpec` 里规定事件，而不是由多关系过程后验形成事件。

# 四、现在怎样处理已经落地的代码？

最稳妥的做法不是删除，而是**降级解释、冻结扩展**。

## 方案一：只修文档和命名含义

暂时保留现有类名，以免引起不必要的代码返工，但在文档和 docstring 中明确：

```text
EventKernelSpec:
目前仅为事件核所需的关系谱系候选规格，
不表示已经取得事件核资格。

EventInstanceCandidate:
目前仅表示关系支撑谱系完整的候选绑定，
不表示 D3 事件实例。
```

并把当前状态写成：

[
\texttt{CANDIDATE_LINEAGE_BOUND}
]

而不是宽泛的：

[
\texttt{CANDIDATE}.
]

这是改动最小的做法。

## 方案二：正式重命名

更严格的话，可以改为：

```text
RelationSupportSpec
RelationLineageBinding
RelationStructureCandidate
```

对应阶段改名为：

[
\boxed{\text{P2-B1X：关系实例谱系绑定}}
]

这样理论和代码完全一致。

不过这不是当前阻塞项；核心是停止继续把它扩展成事件状态机。

# 五、两个需要登记的非阻塞限制

## 1. “局部作用”目前可能只是测试证明

P2-B1R 的局部作用来自录制—回放测试。

如果 `EventSupportBinding` 在生产运行时只接收一个布尔量，例如：

```text
local_effect_qualified=True
```

那么它绑定的是一张离线资格证，而不是在线发生的实际局部电流实例。

这并非错误，但应区分：

[
\begin{aligned}
Q_{\rm local_effect}^{\rm type}
&=\text{这种 bundle 类型已证明能够局部施力};\
I_{\rm local}^{\rm instance}(t)
&=\text{这一次运行中实际测得的局部作用}.
\end{aligned}
]

当前很可能只拥有前者。

## 2. “缺少支撑即拒绝”是类型验证，不是必要性证明

T-EKB-2 移除某个字段后拒绝 candidate，证明的是：

> 规格要求这些字段。

它还没有证明：

> 在真实动力过程中移除该结构，未来作用必然消失。

前者是 schema 完整性；后者才是因果必要性。

因此当前不能把：

[
Q_{\rm support}=1
]

解释为：

[
\text{所有支撑都已通过物理必要性干预验证}.
]

# 七、真正的下一步

[
\boxed{\text{停止 P2-B1K1，开始 P2-C 的最小关系—关系生成。}}
]

P2-C 首先应选两条已经有物理谱系的关系，例如：

[
\rho_{A\prec B},
\qquad
\rho_{B\prec C},
]

构造一个不等同于简单并列的新关系候选：

[
\chi_{\rho\rho}
===============

\mathcal G_{\rho\rho}
\left(
\rho_{A\prec B},
\rho_{B\prec C}
\right).
]

然后验证：

1. 两条父关系具有正确的 D2→D1 谱系；
2. 组合结构由真实电路承载；
3. 去掉任一父关系后组合响应改变；
4. 组合不是单独任一父关系的重命名；
5. 组合是否具有独立未来作用。

只有这种组合结构成立后，`EventKernelSpec` 才可能从“预设规格”转为：

> 对一个已经后验形成的关系组织抽取连续条件。
