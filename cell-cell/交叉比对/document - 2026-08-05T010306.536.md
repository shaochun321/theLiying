`EntryBoundaryDetector`正确区分了：

[

]

因此原始脉冲列：

[
p_\alpha(t)=

]

被实时转为：

[
b_\alpha^\uparrow(t)
====================

\begin{cases}
1,&\text{该持续发生首次进入},\
0,&\text{同一发生中的后续重复脉冲}.
\end{cases}
]

这确实消除了上一轮 (H_\tau) 响应被重复发火重新充电的问题。三态状态机、统一的 `gap_steps=500`、构造签名封闭和跨站点统一参数也都符合接口级要求。

## 当前唯一关键问题：它仍然是软件状态机

现在的因果链是：

[
\texttt{collector.activation}
\rightarrow
\texttt{EntryBoundaryDetector.update()}
\rightarrow
b_\alpha^\uparrow.
]

`CollectorBoundaryPort`只是暴露真实物理载体已经产生的信号，所以可以作为INFRA接口。

但 `EntryBoundaryDetector`做了更多事情：

* 保存 `ARMED/ACTIVE/REFRACTORY` 状态；
* 计算无脉冲间隔；
* 判断500步后发生结束；
* 抑制同一次发生中的后续脉冲；
* 产生新的首次进入脉冲。

这已经不是单纯读取接口，而是一个真正的过程变换：

[
\mathcal E^\uparrow:p_\alpha(t)\mapsto b_\alpha^\uparrow(t).
]

如果它只存在于Python控制逻辑中，那么它目前是：

[

]

还不是项目要求的：

[
\boxed{\text{由物理结构实现的发生边界生成算子。}}
]

否则项目会从“由Occurrence事后重建过程”修正为“由软件状态机实时生成过程”，虽然因果方向正确了，但物理实现问题仍未解决。

## `gap_steps=500`也要区分两种资格

作为仿真判定规则：

[
gap_steps=500
]

有已有实测依据，可以接受。

作为物理算子参数，它还需要对应到：

[
\tau_{\mathrm{gap}}=500\Delta t,
]

以及实际承载这个时间保持的结构，例如：

* 电容泄漏时间常数；
* 门控状态；
* 不应期结构；
* 锁存与释放结构；
* 或明确建模的物理计数器。

目前的整数计步本身还没有说明由哪个物理结构保存。
