这份报告有一个很有价值的新发现：

[
\boxed{\text{共同源关系不等于两条R1活动必须瞬时同步。}}
]

因此我不同意把当前问题简单归类为“R2 collector还需要调参”。

## 当前裁定

基础设施部分通过：

* T1、T2真实活动进入R2层，而不是读取两张记录后硬生成；
* 两条R1共享同一个站点28物理结构；
* `R2ForkFinalizer`能核验相同的 `OccurrenceInstanceId`；
* 不同epoch即使地址相同也会被拒绝。

但：

[
\boxed{\text{P2-C1F尚未完成，只完成了P2-C1F-a基础设施。}}
]

因为真实场景中：

[
R1_{28\prec31}=1,\qquad
R1_{28\prec23}=1,\qquad
R2_{\rm fork}=0.
]

还没有实际产生过正式 `R2Occurrence`。

---

# 唯一阻塞：当前R2的AND条件过强，而且可能定义错了

现在R2 collector要求：

[
x_{R1,T1}(s)>\theta
\quad\land\quad
x_{R1,T2}(s)>\theta
]

在同一时刻成立。

但共同源分叉真正要求的是：

[
\operatorname{source}(R1_{T1})
==============================

# \operatorname{source}(R1_{T2})

u_{28,n}.
]

两条通路距离、耗散和响应延迟不同，所以完全可能是：

```text
站点28同一次发生
   ├─ 稍早形成 28≺31
   └─ 稍后形成 28≺23
```

它们仍然是同一共同源分叉，只是两个R1的检测峰没有瞬时重叠。

如果为了让峰值重叠而反复调整热源温度、持续时间，可能会引入新的技术债：

> 用外部输入强行配合AND门，而不是让R2机制表达共同源关系本身。

---

# 最合适的低成本修正

不要搜索HeatSource参数，也暂时不要改变T1/T2。

在R2输入侧为两条R1各增加一个短时物理保持痕迹：

[
R1_{T1}
\rightarrow
z_{T1}^{R2},
]

[
R1_{T2}
\rightarrow
z_{T2}^{R2}.
]

然后R2 collector读取：

[
z_{T1}^{R2}(s)
\land
z_{T2}^{R2}(s).
]

痕迹由各自R1 collector真实活动触发并自然衰减，不读取 `RelationOccurrence` 内容。

结构是：

```text
T1 relation collector → R2 trace 1 ─┐
                                    ├→ R2 fork collector
T2 relation collector → R2 trace 2 ─┘
```

这样允许：

* 两条R1自然存在时间差；
* 只要在共同源物理区间内先后发生，就能组合；
* 不要求不自然的瞬时同步；
* 仍然是实际神经动力链路；
* 不依赖软件记录生成R2。

---

# 共同源身份仍由Finalizer核验

物理R2 collector只负责产生候选：

> 两条R1活动在同一局部区间内出现。

随后 `R2ForkFinalizer`继续核验：

[
parent_{28}^{T1}
================

parent_{28}^{T2}.
]

因此形成两道门：

[
\boxed{
\text{物理活动重叠门}
+
\text{共同父实例谱系门}.
}
]

前者防止纯软件组合，后者防止把不同epoch的站点28错误绑定。

---

# 不建议采用的方案

暂不建议：

* 扫描热源温度和持续时间；
* 直接放宽R2 collector阈值；
* 直接读取两个 `RelationOccurrence` 后创建R2；
* 把R1 collector的时间常数随意加长。

最后一种会改变已经冻结的R1语义。保持痕迹应属于：

[
\boxed{\ell_{\rm gen}^{R2}}
]

而不是回头修改T1/T2。
