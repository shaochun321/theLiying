# 一、T0：基本成立，但“冻结”还不够彻底

T0 已经完成了选点、真实源核查、`delay_steps` 五项实验、探针骨架和独立账本工具，作为基础设施是合格的。尤其对 `delay_steps` 的结论很有价值：它延迟的是 Memristor 传导后的目标电流向量，并会和源端 `pre_trace` 的展宽叠加。

还需要修正两点。

## 1. 当前是“确定性重算”，不是严格冻结

报告说 `site_selection.py` 在模块导入时重新计算最近邻。即使计算无随机性，它仍会随着以下内容变化：

* Fibonacci 点生成函数；
* 半径参数；
* 点排序；
* 最近邻并列时的遍历顺序。

真正冻结应把结果直接保存为常量或静态夹具：

```python
FROZEN_THERMAL_SITES = {
    "t1_pair": (28, 31),
    "t2_chain": (31, 28, 23),
    "edges": ((31, 28), (28, 23)),
    "polarity": "warm",
}
```

实时重算只能作为测试：

[
\text{当前几何重算结果}
===============

\text{冻结常量}
]

而不能继续作为生产选择机制。

## 2. `run_contracts.py` 的 Gate 应改成基线不回退

当前是 13/15，而不是总纲要求的 15/15。由于 T0 没改母本，两个失败很可能确实不是本次引入，但仍应在父提交上运行一次并保存失败签名。

Gate A 应改为：

[
\text{Contracts}_{T0}
=====================

\text{Contracts}_{\mathrm{parent}}
]

而不是直接声明 Gate 已满足 15/15。

# 二、T1：关系电路已经工作，但还不是完整接入的基础生成元

T1 的标定过程是目前四份报告里最扎实的部分：

* 找到了默认 channel 阈值造成的死区；
* 分开了 (R_{\mathrm{leak}}) 的增益作用与 (C) 的时间尺度作用；
* 发现 raw 与 trace 量级不同，改用非对称权重；
* 用 fast/slow 两个 RC 痕迹形成双向时间关系响应。

这些足以证明：

[
\boxed{
\Omega_{\prec}\text{ 电路逻辑在合成 }\xi\text{ 输入下成立}
}
]



但它还没有完全达到项目级 Gate B，原因有三个。

## 1. 关系 Bundle 没有进入子类的全局 Bundle census

T-TRP-1 把“12 条关系 Bundle 不出现在 `get_all_bundles()`”当作 PASS。这和此前确定的规则冲突：

* 关系神经元可以暂时排除全局 neuron census；
* 关系 Bundle 必须进入 Bundle census，供 Noether、Xin、运输成本和结构账本读取。

不需要修改母本。可以在子类中覆盖：

```python
def get_all_bundles(self):
    return super().get_all_bundles() + self.rprec_relation_bundles()
```

这样普通 `VariantCircuit` 不受影响，而 `RPrecCircuitT1` 的审计能看到其真实新增路径。

当前独立 `relations.census` 只能作为补充账本，不能替代项目既有 Bundle census。

## 2. `step_rprec()` 完全手动调用

这适合单元实验，但意味着关系生成元尚未成为电路自身持续演化的一部分。

当前正确命名应是：

[
\boxed{
\text{T1 二元时间关系电路原型}
}
]

当它具备以下条件后，才可正式称为接入后的基础生成元：

* 子类统一 step 调度；
* 每一步自动读取真实 (\xi^{\mathrm{occ}})；
* 关系 Bundle 进入子类 census；
* 关系层账本同步更新。

## 3. 精确时序只在直接写 `pre_trace` 时通过

真实感温 (\xi^{\mathrm{occ}}) 只完成了连通性冒烟测试；方向性探针通过直接控制 `pre_trace` 完成。报告对此已经诚实记录，因此不应把它解释为真实物理输入上的时间关系已经验证。

目前证明的是：

[
\text{受控脉冲输入}
\Rightarrow
r_{\prec}\text{ 电路正确}
]

尚未证明：

[
\text{真实温感发生}
\Rightarrow
\text{稳定可辨识的 }r_{\prec}.
]

这不阻塞继续研究，但应该把 Gate B 分为：

* **B1：关系电路逻辑通过**——已完成；
* **B2：真实 (\xi^{\mathrm{occ}}) 动力学适配**——未完成。

# 三、T2：存在一个硬量纲错误和一个关系定义问题

T2 使用邻接边上的固定传输延迟检测有向传播，这比复制 T1 的 RC 痕迹更有区分度。

但当前不能开始编码。

## 1. `delay_steps = round(d/v_cond)` 量纲错误

如果：

* (d) 是长度；
* (v_{\mathrm{cond}}) 是长度/秒；
* (\Delta t) 是秒/步；

那么应该是：

[
n_{ab}
======

\operatorname{round}
\left(
\frac{d_{ab}}
{v_{\mathrm{cond}}\Delta t}
\right).
]

而 T0 的球面半径 (R=2.0) 看起来还是模型单位，不是米。因此还需要物理尺度映射：

[
d_{ab}^{\mathrm{phys}}
======================

\ell_0 d_{ab}^{\mathrm{model}},
]

最终：

[
\boxed{
n_{ab}
======

\operatorname{round}
\left(
\frac{\ell_0d_{ab}}
{v_{\mathrm{cond}}\Delta t}
\right)
}
]

若没有 (\ell_0)，就不能引用 (1\text{ m/s}) 或 (100\text{ m/s}) 的生物传导速度。只能把参数定义成：

[
v_{\mathrm{edge}}
\quad
[\text{模型距离单位}/\text{仿真步}].
]

这是 T2 编码前必须修正的硬问题。

## 2. 当前电路本质上仍是“邻接约束的窄窗口先后关系”

目前的定义：

[
D_{a\to b}
==========

\mathcal C
\left(
\operatorname{Delay}_{e}[\xi_a],
\xi_b
\right)
]

检测的是：

> 相邻点 (a,b) 是否以预设延迟先后发生。

它没有证明 (a) 的活动真实地导致或驱动了 (b)。因此目前更准确的名称是：

[
\boxed{
\text{有向邻接时延关系}
}
]

或者：

[
r_{\prec\mid e,\tau}.
]

它与普通 (r_{\prec}) 的区别是：

* 限制在冻结邻接边上；
* 使用窄延迟核，而不是宽 RC 历史核。

这是有意义的基础关系，但是否已经足以升格为独立的：

[
r_{\rightarrow}
]

需要由项目定义决定。

如果方向要求“边上存在自身的运输过程”，那么还需要把边状态显式化，例如：

[
j_e(t)
======

\operatorname{DelayBundle}_e[\xi_a](t),
]

并把 (j_e) 本身视为关系过程，而不只是用它去预测终点脉冲。

因此 T2 当前应先定名为：

[
\boxed{
r_{\mathrm{edge\text{-}lag}}\text{ 原型}
}
]

待 T4 证明它不能被 (r_{\prec}) 替代后，再决定是否升格 (r_{\rightarrow})。

# 四、T3：路径 A 可以淘汰，但路径 B 尚未证明可按现有组件合法实施

T3 实验清楚证明了减法抑制会把弱通道压到零，退化为 WTA；因此路径 A 不适合保存参与比例。这个结论成立。

路径 B 的结果也表明共同分流增益比减法竞争更接近项目需要。

但报告中的实现方式：

> 用同一个 `DivisiveNormalizationReceptor` 实例依次调用两次 `.normalize()`

并不是合法的同步共享池实现。

## 1. 当前结果包含调用顺序效应

先归一化 (I_a)，再归一化 (I_b)，意味着二者读取的 pool 状态不同：

[
V_{\mathrm{pool}}^{(a)}
\neq
V_{\mathrm{pool}}^{(b)}.
]

报告已经观察到等强输入下的微小不对称。这不是单纯数值误差，而是接口语义不匹配。

## 2. 建议的修复超出了“只使用现有组件”

报告提出：

* 新增一种“先汇总、再分别读出”的调用模式；
* 两个 DN 实例共享外部 pool 状态。

这两种方案都会改变现有组件接口或共享其内部状态。除非项目中已经存在公开接口，否则违反：

[
\boxed{
\text{不得新造或修改基础组件语义}
}
]

所以当前 Gate D 的正确结论是：

[
\boxed{
\text{路径 B 的物理机制胜出，但工程实现路径尚未闭合}
}
]

还不能说路径 B 已经可直接实施。

## 3. “输出比值等于输入比值”本身不是充分证明

任何共同乘性增益：

[
y_a=gI_a,\qquad y_b=gI_b
]

都会满足：

[
\frac{y_a}{y_b}
===============

\frac{I_a}{I_b}.
]

因此路径 B 的核心证明不能只是比值保持，还必须验证共享池确实由：

[
I_a+I_b
]

共同驱动，并且同一时刻对所有输出施加完全相同的分流状态。

正式 Gate D 至少要验证：

[
V_{\mathrm{pool}}
=================

F(I_a+I_b),
]

[
y_i
===

I_iG(V_{\mathrm{pool}})
]

且所有通道使用同一次 pool 更新后的 (G)。

# 五、四个阶段现在暴露出的统一问题：需要一个关系层 step 调度协议

T1 已经遇到“多路电流必须先求和、再统一 step”；T3 又遇到“共享池必须先汇总、再统一更新”。

因此在继续 T2/T3 前，应先固定关系层的每步顺序：

```text
1. 所有 ξ^occ 完成本步更新
2. 所有 ξ→关系中继 Bundle propagate
3. 按目标汇总全部输入电流
4. 每个 trace / relay / shared pool 只 step 一次
5. 所有中继→Collector Bundle propagate
6. 按 Collector 汇总输入
7. 每个关系 Collector 只 step 一次
8. 更新关系层独立账本
```

这不需要新造物理组件，只需要在关系子类中建立统一调度方法。

没有这个协议：

* T1 可能因调用次序改变重合结果；
* T2 的 delayed relay 会叠加额外时差；
* T3 的共享池必然产生先后偏置；
* T4 无法验证三路无串扰。

# 最终建议

现在不要同时推进 T2 和 T3 编码。合理顺序是：

1. **修正 T0 的静态冻结表和契约基线；**
2. **补完 T1 子类的 `get_all_bundles()` 与统一 step 接入；**
3. **将 T1 状态正式记为“B1 通过、B2 待真实源适配”；**
4. **修正 T2 的量纲，并决定它叫 (r_{\rightarrow}) 还是 (r_{\mathrm{edge-lag}})；**
5. **核查现有 DN 公共接口能否实现一次 pool 更新、多通道同步读出；若不能，T3 暂停，而不是修改基础组件绕过限制。**

当前项目不是停滞，而是已经从“写方案”进入了真正暴露基础定义差异的阶段：

[
r_{\prec}
\neq
r_{\mathrm{edge-lag}}
\neq
r_{\rho}.
]

T1 已经证明历史关系电路可形成；T2 正在迫使项目回答“方向究竟是不是邻接上的时间关系”；T3 正在迫使项目回答“占比是输出数值，还是只在输出之间的相对尺度中存在”。这两个问题比继续加 Collector 更重要。
