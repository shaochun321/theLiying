## 裁定

P1-C0 的核心方向正确：它第一次把世界、皮肤、热源和有序传输放进同一个“快照—校验—提交—回滚”周期，并实际关闭了 B3 遗留的三处调用纪律漏洞。9 项专项测试、43 项相关测试及 21/21 回归均通过。 

但暂时不宜宣称 C0 已经完全冻结。进入 C1 前，有四个边界需要直接纳入 C1 的入口修正，不必再新建“C0.5”。

# 一、必须补：皮肤端的联合稳定性预算

当前公式只明确给出了世界节点预算：

[
\eta_{w,i}
==========

\Delta t
\left[
\frac{
\sum_j\kappa_{ij}
+\sum_sH_{is}
+G_i^{env}
}{C_i}
+
\sum_{e:\mathrm{tail}(e)=i}a_e
\right]
\leq1.
]



但 C0 已允许多条接触边共享同一个皮肤状态，并验证了通量求和。

如果多个世界节点同时连接皮肤 (s)，皮肤端也需要：

[
\boxed{
\eta_{s}
========

\Delta t
\frac{
\sum_iH_{is}+G_s^{env}
}{C_s}
\leq1.
}
]

当前皮肤默认没有环境泄漏，因此现阶段可取：

[
G_s^{env}=0.
]

P0 已明确默认皮肤泄漏为零。

否则可能出现：

* 每个世界节点分别安全；
* 世界侧联合预算也安全；
* 但多个接触通量集中到同一皮肤，使皮肤侧显式更新失稳。

现有夹具 B 是“一世界节点—两皮肤”，主要验证世界端的 (\sum_sH_{is})。还应增加反向夹具：

[
\boxed{
\text{两世界节点—同一皮肤—两条接触边}
}
]

专门验证皮肤端：

[
\sum_iH_{is}.
]

# 二、必须补：异常回滚要恢复图级诊断账本

报告称异常时会完成世界、皮肤和热源三方完整回滚，但所述完整状态主要是节点电容的：

[
(q,_q_{\mathrm{in}},_q_{\mathrm{out}}).
]



问题在于 `ThermalFieldGraph.step()` 还会更新图级的本步诊断快照：

* `_last_injection`；
* `_last_leak`；
* `_last_divergence_dt`；
* `_last_charge_before`。

这些字段被 `closure_residual()` 用于节点级守恒读出。

如果过程是：

1. `world_graph.step()` 成功；
2. 皮肤写入异常；
3. 节点 charge 被恢复；
4. 图级 `_last_*` 没有恢复；

就会形成：

[
\boxed{
\text{物理状态已回滚，观测账本仍记录失败步骤。}
}
]

这会产生幽灵发生记录，并污染以后 L2/P2 的关系读出。

因此回滚快照必须包含图级诊断字段，或者异常时显式恢复到提交前的图级快照。

应增加测试：

> 皮肤侧异常回滚后，所有节点状态、热源状态以及 `closure_residual()` 所依赖的 `_last_*` 字段均与提交前完全一致。

# 三、运行实例绑定仍需收紧

当前：

```text
runtime_uid = id(world_graph)
```

确实能区分两个内容相同但对象不同的世界图。

但它还存在两个边界。

## 同一世界图可以被包装成两个 runtime

若创建：

```text
runtime_A = JointThermalRuntime(world_graph)
runtime_B = JointThermalRuntime(world_graph)
```

两者：

[
runtime_uid_A=runtime_uid_B
]

却分别持有新的 `AppliedPlanRegistry`。

这样可能重新引入“双重提交通过新的登记表绕过”的问题。

`runtime_uid` 应当在 `JointThermalRuntime` 构造时生成一次独立 UID，而不是直接等于 `id(world_graph)`。

## 当前 UID 只绑定世界图

联合计划还涉及：

* 皮肤状态；
* 热源；
* 接触边；
* locator。

如果同一世界图配上另一组状态完全相同的皮肤或热源，仅靠世界图 UID 和内容快照未必能区分。

更完整的契约应是：

[
\alpha_{\mathrm{runtime}}
=========================

H(
\text{runtime instance},
\text{world instance},
\text{skin instances},
\text{source instances}
).
]

工程上不必真的哈希；可以让 `JointThermalRuntime` 长期持有所有参与对象，并在计划中记录该 runtime 自己生成的不可变 UID。

至少增加两个测试：

* 两个 runtime 包装同一个世界图，计划不能跨 runtime 提交；
* 同一世界图但替换为状态相同的另一皮肤或热源，提交必须拒绝。

# 四、热源预览复制了 `release()` 语义

C0 为了在 prepare 阶段保持只读，复制了 `DynamicHeatSource.release()` 的计算公式，并在 apply 阶段直接扣减冻结的 `source_actual_energy`，不再调用 `release()`。

这解决了原子性，但出现了新的双实现风险：

```text
DynamicHeatSource.release()       # 原正式机制
joint plan 内部复制的计算公式      # 第二份机制
```

以后若 `release()` 增加：

* 效率变化；
* 输出限制；
* 账本字段；
* 耗尽状态转换；

联合层可能继续使用旧公式。

建议把热源释放计算变成单一事实源：

```text
preview_release(dt)   # 纯只读，返回计划释放量
commit_release(amount) # 提交冻结量
```

或者由一个共同的纯函数计算：

[
E_{\mathrm{actual}}
===================

F(E_{\mathrm{remaining}},P,\eta,\Delta t),
]

`release()` 和联合 prepare 都调用它。

这属于接口抽取，不是新增物理机制。
