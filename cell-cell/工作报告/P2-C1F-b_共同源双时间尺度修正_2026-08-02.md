## 一、目标

评判指出P2-C1F的核心概念错误：把"共同源"等同于"两条R1活动瞬时同步"。
28≺31（d=1.09）和28≺23（d=1.16）两条通路物理距离不同，响应延迟自然
不同，站点28的同一次发生完全可能先形成一条R1、稍后形成另一条，仍是
同一共同源分叉。要求：不搜索HeatSource参数，不改T1/T2本身，不放宽
R2 collector阈值，不直接读RelationOccurrence生成R2（纯软件组合）。
正确做法：给R2输入侧加trace中继层，让两条自然错开的R1活动能在衰减
窗口内产生物理重叠。

## 二、实际改动

`nexus_v1/relations/r2_fork.py`：

**新增R2 trace中继层**（`r2_trace_t1`/`r2_trace_t2`）：
- R1 collector → trace（权重复用T1的`_W_XI_TO_TRACE=0.3`）
- trace → R2 collector（权重复用T1的`_W_TRACE_TO_COLLECTOR=0.5`）
- 参数全部复用T1的fast trace标定值（tau=50步），不重新标定

**修正`R2ForkFinalizer.step()`的核验时序**（真正的根因修复）：
- 原逻辑：R2 collector上升沿时立即读取`completed_relations[-1]`做核验
- 新逻辑：R2 collector上升沿只记录候选时刻`_pending_since`，之后每步
  检查T1和T2是否都已产生正式`RelationOccurrence`，都产生后才做共同源
  核验并生成`R2Occurrence`（`t_detect`用真实的R2上升沿时刻，不是核验
  完成的时刻）

## 三、发现的真实问题

### 3.1 trace中继层本身不足以解决问题（诊断脚本实测）

加了trace层后T-R2F-3仍是INFO（R2=0）。诊断显示：

```
T1 t_detect=530, T2 t_detect=535, gap=5   # collector检测本身几乎同步
max_r2col_pretrace=1.578                  # R2 collector确实越阈了（远超0.15阈值）
```

R2 collector本身工作正常，问题在`R2ForkFinalizer`。继续诊断发现：

```
R2 collector rising edges: [564]（只有一次，t=564）
T1 RelationOccurrence t_closed=1289
T2 RelationOccurrence t_closed=1559
```

R2 collector在t=564就已经上升沿又衰减完毕，但T1的`RelationOccurrence`要到
t=1289才闭合，T2要到t=1559——R2 collector的物理响应窗口（trace tau=50步
量级）和T1/T2走完`rearm_min_steps=500`延迟所需的时间（500+步量级）完全
不在同一尺度。这不是trace窗口开得不够宽的问题（开多宽都补不上10倍以上
的量级差），是核验时序本身选错了检查点。

### 3.2 根因修复验证

修正`R2ForkFinalizer`后：`R2Occurrence.t_detect=564`（保留真实的R2物理
上升沿时刻）、`t_closed=1560`（T1/T2都闭合后的时刻）——时序链路完整，
不是拼凑数字。
