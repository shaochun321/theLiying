## 背景

评判要求实施P2-B1X1（把"测试手工构造关系"改成"D1在线transition→collector自然激活→创建草稿→自动回填→正式RelationOccurrence"）。

在动手写`RelationDraft`/`OccurrenceIdentityRegistry`/`RelationOccurrence`之前，先调研了评判假设的地基是否存在，发现两个缺口：

1. **`Occurrence`没有per-instance地址**——同一generator反复产生的所有occurrence共享同一个`address`（如`"thermpt28_warm"`），区分"这一次"和"上一次"的`epoch_id`只活在`OccurrenceClosure`内部计数器和`TransitionEvent`里，从未进入`Occurrence`本身。
2. **`RPrecCircuitT1`的collector完全没接入occurrence系统**——`rprec_xi_a`/`rprec_xi_b`（`temporal_r_prec.py:225-228`）是裸`Neuron`引用（`thermal_quantum_collectors`），relations层对generators层零import、零`OccurrenceClosure`绑定。

如果不先补这两块地基，P2-B1X1的四个测试仍会退化成"测试手工拼字符串模拟完成回填"——重复P2-B1X本身的错误。

## 地基1：Occurrence增加epoch_id（已完成，未提交）

### 改动

`nexus_v1/generators/occurrence.py`：

```python
@dataclass(frozen=True)
class Occurrence:
    t_up: int
    t_down: int
    t_rearm: int
    address: GeneratedAddress
    epoch_id: int          # 新增字段
    count: int = 1
```

`OccurrenceClosure.update()`的REFRACTORY分支构造`Occurrence`时新增`epoch_id=self._epoch_id`（该内部计数器本已存在，只是此前只流向`TransitionEvent`，未流向`Occurrence`）。

### 影响面

全仓库只有一处`Occurrence(...)`构造点（`occurrence.py:294`），`naturalize()`（`natural_unit.py`）不读`epoch_id`，无需改动。

## 地基2：RPrecCircuitT1接入真实occurrence系统（设计中，未落代码）

### 目标

让`rprec_xi_a`/`rprec_xi_b`（站点28/31的warm collector）在被真实驱动时，各自产生带`(address, epoch_id)`的正式`Occurrence`，供后续`RelationDraft`回填地址用。

### 方案对比

**方案甲：RPrecCircuitT1内部wrap两个BaseGenerator**

用`wrap_base_generator(self, site_a, registry, polarity="warm")`拿到`BaseGenerator`句柄，复用其`closure`和`tick_from_skin()`。

- 优点：完整复用地址注册（`register_occ_thermal`）和门控逻辑（`phys_support = l1.activation > 0`），不用重新发明。
- 风险：`base_generator.py:171-182`明确警告——`VariantCircuit._step_quantum_thermal_pathways`在每次`circuit.step()`时已经用world/body真实采样驱动同一批l1/hc/ensemble/collector对象；若调用方还调用`tick()`/`tick_from_skin()`会造成同一pathway每步被驱动两次（真实world dT + 合成dT叠加）。`RPrecCircuitT1`是`VariantCircuit`子类，它的`xi_a/xi_b`本来就已经在`circuit.step()`主循环里被驱动——如果再wrap一层`BaseGenerator`并调用其`tick()`，正好撞上这个互斥警告。

**方案乙：只给现有collector外挂一个OccurrenceClosure，不经过BaseGenerator/wrap**

直接在`RPrecCircuitT1.__init__`里构造两个裸`OccurrenceClosure(address=...)`（复用`register_occ_thermal`拿地址，但不经过`wrap_base_generator`/`BaseGenerator`），新增一个方法（如`step_rprec_with_occurrence(t_step)`），在其中调用`closure_a.update(xi_a.pre_trace, t_step, phys_support=?)`。

- 优点：不涉及`BaseGenerator`的驱动权守卫，不产生双重驱动风险；`xi_a`/`xi_b`的电流传播完全交给母本`circuit.step()`或`RPrecCircuitT1`已有的`step_rprec()`，`OccurrenceClosure`只是在外部"多读一次"`pre_trace`做记账，不改变电路行为（这正是`occurrence.py`模块文档Q2的既定定位："纯粹读取既有collector.pre_trace的状态机记账层"）。
- 待解决：`phys_support`参数从哪来。

### 未决问题：phys_support信号源

`BaseGenerator.tick()`用`self.l1.activation > 0`作为`phys_support`（`base_generator.py:213-219`的P2-A1b-3R传入门控修复，防止HC慢态残留触发伪occurrence）。这是经过实测标定的机制（900驱动+15000撤去场景实测14次伪occurrence→1次），**不是可以跳过的细节**。

`RPrecCircuitT1`当前拿不到"L1"这个概念——它直接引用的是`thermal_quantum_collectors`（AND门collector，在`_init_quantum_thermal_pathways`链条的下游），L1（`ThermalDeltaNeuron`）在`circuit.thermal_quantum_l1_warm[f"thermpt{site}"]`，是同一条通路的上游对象，母本`VariantCircuit`本身就持有它，只是`RPrecCircuitT1.__init__`此前没有取用。

**候选做法**：在`RPrecCircuitT1.__init__`里补取`self.rprec_l1_a = self.thermal_quantum_l1_warm[f"thermpt{site_a}"]`（对b同理），`phys_support`用`self.rprec_l1_a.activation > 0`——这与`BaseGenerator.tick()`的门控逻辑完全一致，只是不经过`BaseGenerator`这层包装，直接引用母本对象（符合RULES.md"不修改母本代码添加功能"，这里只是多存一个既有对象的引用，不新建、不改母本）。

**需要交叉比对确认的点**：
1. 方案乙（外挂OccurrenceClosure，不经过BaseGenerator包装）是否符合评判对"在线闭环"的要求，还是评判期望的是`RelationDraft`直接消费`BaseGenerator.tick()`的返回值（即要求`RPrecCircuitT1`改用`wrap_base_generator`驱动，接受双重驱动风险需要额外规避）？
2. 如果采用方案乙，`OccurrenceClosure`的`theta_up`/`theta_down`/`rearm_min_steps`是否直接复用`occurrence.py`模块级默认值（0.01/0.001/500），还是需要针对`RPrecCircuitT1`已有的collector标定（该collector本身阈值`_COLLECTOR_THRESHOLD=0.15`，量级与L1/HC层不同，直接套用默认值是否合理）？

## P2-B1X1本身：暂定方案（待地基2确定后落地）

三个生产对象（`nexus_v1/relations/relation_lineage.py`或类似位置，暂不确定文件归属）：

1. `RelationDraft`：collector越过阈值时创建，字段对齐评判给出的清单（`relation_type`/`parent_a_generator_address`/`parent_a_epoch_id`/...），状态`OPEN_RELATION_DRAFT`。
2. `OccurrenceIdentityRegistry`：`(GeneratorAddr, EpochID) ↔ OccurrenceAddr`映射，D1完成后登记。
3. `RelationOccurrence`：A、B两个父实例都取得正式身份后自动完成的正式D2关系实例。

**关键语义**（评判强调，必须遵守）：`RelationOccurrence`的生成**不依赖DA或局部作用资格**——即使DA=0，只要A≺B真实发生，也应产生`ρ_obs`。P2-B1R的局部电流资格（`I_local^type`）只挂在关系载体类型/学习结果上，不作为每个关系实例成立的必要条件。

四个测试（T-RLI-1~4）设计从评判原文直接搬入，暂不改动。
