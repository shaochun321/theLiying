## 一、评判诊断

评判发现了根本性理论定位问题：

> **代码做的是"关系谱系绑定"，名称和阶段却被升格成了"事件元支撑绑定"。**

### 实际完成的

```
ρ_{A≺B}^{(2)} → (u_{A,i}^{(1)}, u_{B,j}^{(1)}) → 物理支撑
```

- ✓ D2关系绑定到正确的两次D1 occurrence
- ✓ 补齐D2→D1→D0完整谱系
- ✓ 验证跨epoch错配（实例身份vs站点身份）
- ✓ collector、bundle、局部作用证明

### 当前未完成的（需P2-C后）

- ✗ 支撑在真实运行中何时同时出现
- ✗ 支撑如何连续维持
- ✗ 事件何时进入/退出/重新可用
- ✗ 这些支撑共同形成独立于单条关系的组织
- ✗ 候选结构具有新的未来作用

因此`CANDIDATE`实际含义：**关系谱系材料完整且一致**，不是：**事件候选已由过程生成**。

## 二、为何会发生偏移

1. **跳过P2-C**：如果现在做P2-B1K1（事件核连续状态机），会把单条`A≺B`关系预设成一个事件类型
2. **绕过后验形成**：真正的事件核需要由多关系组织后验形成，而非开发者规定
3. **升格过早**：当前只完成了谱系基础设施，未证明事件核已开始生长

## 六、真正的下一步

**停止P2-B1K1，开始P2-C的最小关系—关系生成**。

### ⚠ P2-C的前置陷阱（评判2026-07-29T194034补充）

当前工程实际只验证了**一个方向、一个时间尺度**的关系：

```
ρ_{A≺B}^fast   ← 唯一已取得完整资格的关系
```

项目**尚未拥有**已取得同等级资格的 `ρ_{B≺C}`。因此不能直接假装有两条关系可组合。

### P2-C0：先建立第二条同等级关系

两种路线：

**路线A（结构简单）**：相同关系类型，不同occurrence对
```
ρ_{A_i≺B_j}^fast,  ρ_{A_m≺B_n}^fast
```
可测试"关系实例—关系实例"组合，但结构丰富度有限。

**路线B（理论价值更高）**：新增第三个D1来源C
```
ρ_{A≺B}^fast,  ρ_{B≺C}^fast
```
更符合真正的关系—关系生成，但需新增输入站点、关系collector和谱系工作。

评判倾向路线B，但明确要求不能在文档里默认它已存在。

### P2-C1：首次关系—关系生成

两条关系就绪后，构造新关系候选：
```
χ_ρρ = G_ρρ(ρ_1, ρ_2)
```

验证5项资格：
1. 两条父关系具有正确的D2→D1谱系
2. 组合结构由真实电路承载
3. 去掉任一父关系后组合响应改变
4. 组合不是单独任一父关系的重命名（不可约性）
5. 组合是否具有独立未来作用

只有这种组合结构成立后，`EventKernelSpec`才可能从"预设规格"转为"对已后验形成的关系组织抽取连续条件"。
