## 一、目标

在P2-C0（T1/T2两条同等级R1）基础上，构造第一个关系-关系（R2）实例，
验证"同一个D1发生支撑的两条R1关系能否通过新物理链路生成共同源型R2"。
明确不宣称：传递闭包A≺C、散度、因果树、高阶涌现。

评判230002/232255给出的关键约束：
1. 拓扑是共同源分叉（28→31, 28→23），不是传递链（31→28→23）
2. R2输入必须是R1的真实活动（collector.pre_trace），不是RelationOccurrence记录
3. 共同源资格必须核验同一个`OccurrenceInstanceId`（相同地址不同epoch不算共同源）
4. 命名用R2（关系-关系层），不说"D2关系"

## 二、实际改动

新增 `nexus_v1/relations/r2_fork.py`（284行）：

**R2ForkCircuit**（继承`RPrecCircuitT1, RPrecCircuitT2`，MRO验证过）：
- T1/T2各自完整初始化，共享站点28的`thermal_quantum_collectors["thermpt28_warm"]`
  （实测确认`circuit.rprec_xi_a is circuit.rprec2_xi_b == True`）
- 新增`r2_fork_collector`（AND门Neuron，参数复用T1标定值）
- 新增2条frozen bundle：T1 collector→R2 collector，T2 collector→R2 collector
  （权重复用`_W_RAW_XI_TO_COLLECTOR=0.15`，因为两路输入都是"已集成的R1信号"，
  不需要trace积分）
- `step_r2(dt)`：在`step_rprec()`/`step_rprec2()`之后传播R2层

**R2Occurrence**（frozen dataclass）：
- `shared_source_instance_id`：两条R1的共同起点D1实例（评判232255核心要求）
- `parent_r1_t1_key`/`parent_r1_t2_key`：轻量四元组身份键（不持有完整对象引用）
- 无DA字段（同R1的DA独立性原则）

**R2ForkFinalizer**：
- 监听`r2_fork_collector.pre_trace`上升沿
- 上升沿时核验：`t1_ro.parent_a_instance_id == t2_ro.parent_a_instance_id`
  （必须是同一个`OccurrenceInstanceId`，不是"都来自站点28地址"）
- 通过核验才生成`R2Occurrence`，否则跳过（T-R2F-2验证了这个拒绝路径）

新增 `nexus_v1/tests/test_r2_fork.py`（约240行，T-R2F-1~3）。

## 三、发现的真实问题

### 3.1 共同源核验逻辑本身正确工作（T-R2F-2验证）

手工构造T1的`parent_a_instance_id`（站点28，epoch=1）和T2的
`parent_a_instance_id`（站点28，epoch=2，故意设为不同），验证`R2ForkFinalizer`
正确拒绝生成R2Occurrence。这证明"相同地址不同epoch"和"同一个
OccurrenceInstanceId"的区分在代码层面真实生效，不只是文档声明。

### 3.2 R2 fork collector的AND门条件比预期更苛刻（T-R2F-3的INFO结果）

真实驱动场景（热源放在共享站点28）下：
```
occ_28=1, R1(T1)=1, R1(T2)=1, R2=0
```
T1和T2都各自产生了RelationOccurrence（且共同源核验能通过——因为两者确实来自
同一次站点28发生），但R2 fork collector在5000步内始终未越阈。

根因：R2 collector的AND门要求两路输入（T1的`rprec_collector_a_prec_b_fast.
pre_trace`和T2的`rprec2_collector_b_prec_c_fast.pre_trace`）同时处于激活态。
但28→31和28→23是两条物理距离/响应特性略有差异的通路（d=1.09 vs d=1.16），
两条关系各自的检测时刻（`t_detect`）存在自然的时间差，不保证在同一采样窗口
内重叠。这是标定问题，与P2-B1X1d当年遇到的"两条时序关系需要精确时序控制
才能可靠触发AND门"是同一类问题，不是本次新发现的缺陷类型。
